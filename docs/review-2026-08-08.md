# Keturah — functional and code review

**Date:** 2026-08-08 · **Reviewed:** `master` @ `b3ec8a7`, version **0.4.0**
(clean working tree)
**Method:** the public API was exercised directly (manifest → MCP projection →
registry federation), the envelope invariants were probed adversarially, and the
stdio MCP server was driven with well-formed and malformed JSON-RPC. Then the
source was read. Every claim below is backed by a run or a probe, reproduced
inline.

> **Disclosure.** `src/keturah/envelope.py` and `tests/test_envelope.py` were
> written by this reviewer in an earlier session. They are reviewed here on the
> same terms as everything else, and one finding (L1) is against that code.

---

## Part 1 — Functional review

**Baseline:** `39 passed` in 0.04 s. `ruff check src tests` clean, rule set
pinned (`select = ["E4","E7","E9","F"]`) with the explanatory comment, CI gates
both. 1,620 lines total — by far the smallest repo in the estate, and it shows in
the best way.

### What works

The README's examples were run verbatim and all behaved as documented:

```
schema_version: 1.0
to_mcp tools: ['ask']            outputSchema present: True
resources: ['capabilities']      prompts: ['system_prompt']

find('ask')         -> ('tirzah', <Capability ask>)
find('tirzah.ask')  -> ('tirzah', 'ask')
find_all('ask')     -> [('tirzah','ask'), ('milcah','ask')]
reg.to_mcp names    -> ['tirzah.ask', 'milcah.ask', 'milcah.critique']
```

Resources and prompts correctly stay off `to_mcp()`; `outputSchema` is emitted
when set and omitted when not; the Registry namespaces as `product.tool` exactly
as the table promises.

**`validate_manifest` is the most thorough validator in the estate.** Every
adversarial case on the original fields was caught:

```
flagged  duplicate capability names   ['duplicate capability name: ask']
flagged  unknown kind                 ["capability[0] invalid kind: 'wizard' …"]
flagged  empty capability name        ['capability[0] missing name']
flagged  empty product                ['manifest missing product']
flagged  input_schema is a string     ['capability[0] input_schema must be a JSON-Schema object']
flagged  empty description            ['capability[0] (x) missing description']
```

Compare Deborah's `validate_plan`, which accepted duplicate step ids, dangling
dependencies, self-dependency and cycles.

**The shared envelope's documented invariants hold under pressure.** Each was
probed rather than assumed:

```
scalar never back-computed from bands : True
unassessed distinct from low          : True
band thresholds 0.7 / 0.4             : True
band_for(0.0) and band_for(None)      : unassessed

flagged  confidence = 1.4        flagged  confidence = nan
flagged  confidence = -1         flagged  confidence = inf
flagged  terminal_reason bogus   flagged  band bogus
flagged  unknown dimension
```

**The stdio MCP server answers correctly and flushes.** Driven with six frames,
all four valid requests were answered, `tools/call` dispatched to the handler,
and unknown methods returned `-32601`. `_write_json` calls `sys.stdout.flush()` —
the classic stdio-server hang is avoided.

Notably absent: this is the only repo in the estate with **no unanchored
substring matching and no degenerate constant metric**, the two families that
appeared in every other review.

### Functional defects

#### F1. The Stage 0 contract fields are exported as vocabularies and enforced as nothing

`BUDGET_CLASSES` and `CONFIDENCE_MODES` are in the public API:

```python
BUDGET_CLASSES   = frozenset({'free','low','medium','high','unbounded'})
CONFIDENCE_MODES = frozenset({'none','heuristic','calibrated'})
```

None of the fields they govern is validated:

```
ACCEPTED  negotiable = 'yes' (string, not bool)
ACCEPTED  cost budget = 'infinite'          (not in BUDGET_CLASSES)
ACCEPTED  evidence mode = 'vibes'           (not in CONFIDENCE_MODES)
ACCEPTED  failure_modes = 'times out'       (a string, not a list)
```

`validate_capability` returns `[]` for all four. A consumer reading the public
constants will reasonably assume they are enforced, and `failure_modes` as a
string will iterate character-by-character in any consumer that loops over it.

This is the newest release's additions (`b3ec8a7 — Stage 0 contract fields`)
shipping ahead of their validation, in a package whose entire job is being the
place contracts are checked.

#### F2. Capability names may contain the namespace separator

`validate_manifest` accepts a capability literally named `a.b`, and `.` is what
`Registry` uses to separate product from tool. The namespace is therefore not
injective:

```
two manifests: product 'a' with tool 'b', and product 'x' with tool 'a.b'

to_mcp names      : ['a.b', 'x.a.b']
find('a.b')       -> ('a', 'product a, tool b')          ← product x's tool is shadowed
find_all('a.b')   -> [('a','b')]                          ← the other match is OMITTED
find('x.a.b')     -> ('x', "product x / tool 'a.b'")      ← recoverable if you know the product
```

`find_all` is documented as *"every product exposing that tool name"* and here
returns one of two. Nothing warns.

**Exposure is latent, not live** — every family manifest was checked and none
uses a dotted capability name:

```
Tirzah: 6 caps, dotted=none    Hoglah:   2 caps, dotted=none
Milcah: 4 caps, dotted=none    Deborah:  6 caps, dotted=none
Mahalath: 2 caps, dotted=none  Hanani:   6 caps, dotted=none
```

So this is a validation gap to close before it bites, not a live bug.

## Part 2 — Code review

### High

#### H1 · `manifest.py` — `validate_capability` does not check the Stage 0 fields

Code side of F1. The function validates `name`, `description`, `kind`,
`input_schema` and `output_schema` thoroughly, then stops. `negotiable`,
`semantics`, `evidence`, `cost` and `failure_modes` — added in 0.4.0 — pass
unchecked.

**Fix:** four checks, all mechanical.

```python
if not isinstance(cap.negotiable, bool): …
budget = (cap.cost or {}).get("budget")
if budget is not None and budget not in BUDGET_CLASSES: …
mode = (cap.evidence or {}).get("confidence_mode")
if mode is not None and mode not in CONFIDENCE_MODES: …
if not isinstance(cap.failure_modes, list): …
```

The envelope already does exactly this for `TERMINAL_REASONS`,
`CONFIDENCE_BANDS` and `CONFIDENCE_DIMENSIONS`, so the pattern to copy is in the
same package.

#### H2 · `manifest.py` / `registry.py` — `.` is a separator and also a legal name character

Code side of F2. `Registry` splits on `.` to resolve `product.tool`, and
`validate_manifest` permits `.` inside a capability name, so a single string can
denote two different (product, capability) pairs. `find_all`'s omission is the
worst consequence because its whole purpose is exhaustiveness.

**Fix:** reject `.` in `Capability.name` in `validate_capability`. That is
strictly safer than making the resolver smarter, and costs nothing today since no
product uses it.

### Medium

#### M1 · `registry.py` — `to_mcp(namespaced=False)` can emit an invalid `tools/list`

```
to_mcp(namespaced=False) names: ['ask', 'ask']
duplicate MCP tool names emitted: True
```

MCP requires unique tool names in `tools/list`; a client will either reject the
response or silently keep one. The default is `namespaced=True` and is correct,
so this only bites the explicit opt-out — but an API that can produce a
protocol-invalid response should say so rather than emit it.

**Fix:** raise (or warn and namespace anyway) when non-namespaced emission would
collide.

#### M2 · `mcp.py:88-94` — malformed frames produce silence, not a JSON-RPC error

```python
try:
    req = json.loads(line)
except json.JSONDecodeError:
    continue                       # ← no response at all

if not isinstance(req, dict):
    continue                       # ← no response at all
```

JSON-RPC 2.0 §4.2 requires `-32700 Parse error` with `"id": null` for the first
and `-32600 Invalid Request` for the second. Verified: six frames in, four
responses out, and the two malformed ones produced nothing. A strict client
waiting on a response to a corrupted frame will block.

`_error_response` is defined at line 42 and used correctly on every other error
path — this is two `continue`s that should be writes.

#### M3 · `manifest.py:156` — a wrong type on `semantics` raises a raw `dict()` error

```
>>> capability("x", "d", semantics="freeform")
ValueError: dictionary update sequence element #0 has length 1; 2 is required
```

`dict(semantics or {})` leaks its internals. Every other bad type is either
accepted (H1) or reported cleanly by `validate_capability`; this one fails at
construction with a message that does not name the field.

#### M4 · `manifest.py` — an empty `version` validates clean

```
ACCEPTED  no version   (manifest("p", version="", …))
```

The README's premise is that *"Manifest validation requires `schema_version`
equal to `MANIFEST_SCHEMA_VERSION` so consumers can version-gate"*, and the
product `version` is part of what a consumer gates on. `schema_version` is
checked; the product version is not.

### Low

#### L1 · `envelope.py` — `band_for` does not range-check

```
band_for(float('inf'))  -> 'high'
band_for(float('nan'))  -> 'unassessed'
```

`validate_result` correctly rejects `confidence=inf` on a `SpecialistResult`, so
the envelope as a whole is sound — but `band_for` is exported publicly and a
producer calling it directly on an unvalidated number gets `high` for infinity.
The `nan` case is right by accident (comparisons with `nan` are all False, so it
falls through to `unassessed`) rather than by design.

**Fix:** return `unassessed` for any non-finite value, explicitly. *(This is the
reviewer's own code.)*

## Comparison with the Hoglah, Deborah, Tirzah, Milcah, Mahalath and Hanani reviews

Keturah is the cleanest of the seven, and the only one where neither recurring
family appears:

- **No unanchored substring matching.** Hoglah matched on error text, Deborah on
  construct keywords with `re.I`, Milcah on prose markers. Keturah's only
  string-identity operation is the `.` split, and its failure mode (F2/H2) is
  ambiguity in a namespace, not a wrong match.
- **No degenerate constant.** Hoglah's counters, Milcah's `global_coherence`,
  Hanani's all-`True` audit scores. Keturah has no computed metric to get wrong.

Its own finding is a third thing, and a common one in small well-run packages:
**the newest fields shipped ahead of their validation.** The same file that
validates `TERMINAL_REASONS`, `CONFIDENCE_BANDS` and `CONFIDENCE_DIMENSIONS`
rigorously exports `BUDGET_CLASSES` and `CONFIDENCE_MODES` and checks neither.
So this is not a team that doesn't validate — it is one release of new fields
that outran the validator.

That matters more here than it would elsewhere. Keturah is the package the other
six trust to tell them what a contract is; a vocabulary it exports but does not
enforce is a promise the rest of the estate will build on.

The estate-wide property still holds, in its mildest form: **silence**. An
invalid budget class, a shadowed `find_all` match, a duplicate MCP tool name, a
dropped JSON-RPC frame — none logs or raises.

## Suggested order

1. **H1** — four type/vocabulary checks in `validate_capability`. Highest value
   in the estate per line changed, because six products consume these fields.
2. **H2** — reject `.` in capability names. One line, no migration cost (verified
   against all six family manifests).
3. **M2** — replace two `continue`s with `_error_response` writes. The helper
   already exists.
4. **M1, M4, M3** — collision guard, version check, and a clear type error.
5. **L1** — explicit non-finite handling in `band_for`.

Nothing here is architectural. The MCP-projection design is right, the
manifest-from-seam-contracts principle is right, the Registry semantics are
right, and the envelope holds up under adversarial probing. Every finding is a
missing check in a validator that already exists and already does the same job
correctly for its older fields.
